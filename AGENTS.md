# starter

Diese Datei ist zugleich die Vorlage für neue Projekte. Dort ersetzen Titel, „Zweck & Links“, die Prüf-URL unter „Deploy“ und „Fallen“ die Angaben zur Vorlage. „Konventionen“ bleibt und folgt den Änderungen hier, das Nacht-Review prüft alle Prototypen dagegen.

## Zweck & Links

- Vorlage für Web- und Mobile-Prototypen: Bun, Hono, SvelteKit, Drizzle, Postgres, CLI in `apps/cli`, optional Flutter in `apps/mobile`. Neue Projekte: README.md, „Neues Projekt“.
- Selbst nicht deployt. Im Projekt: Live-URL `https://<slug>.pleasance.org`, ab 1.0 eine eigene Domain (README, „Live als 1.0“), Coolify-Projekt `pleasance-<slug>` oder `privat-<slug>`, Ressource `<slug>`.

## Checks

`bun run check && bun run test` (`test` baut das Web und testet den Build, dazu die CLI gegen die API), bei CLI-Änderungen zusätzlich `bun run build` (baut auch die CLI-Datei), bei App-Änderungen zusätzlich `flutter analyze && flutter test && node --test tool/testflight.test.mjs` in `apps/mobile`. Die Browser-Tests starten API und Web auf eigenen Ports (31100, 31101), unter dem ephemeren Linux-Portbereich (32768–60999), damit ausgehende Verbindungen sie nicht kurzzeitig belegen. Testet ein anderer Worktree gleichzeitig, mit anderen Ports unter 32768 aufrufen: `TEST_API_PORT=31102 TEST_WEB_PORT=31103 bun run test`.

## Deploy

- Ein Push auf `main` baut nach grüner CI die Images (nicht bei Änderungen ausschließlich an den unter `paths-ignore` in `ci.yml` aufgeführten Pfaden) und deployt sie über die Coolify-API. Danach fotografiert sie die Live-Seite nach `docs/screenshots/`, committet geänderte Bilder mit `[skip ci]` und meldet den Deploy an `robinchoice/pleasance` (README, „Screenshots“). Ohne das Secret `COOLIFY_TOKEN` überspringt die CI Deploy, Screenshots und Meldung, so auch hier in der Vorlage. Ohne `PLEASANCE_DISPATCH_TOKEN` entfällt nur die Meldung. Pull Requests durchlaufen die CI unabhängig von den geänderten Pfaden.
- App (`apps/mobile`): Ein Push auf `main` baut das Android-AAB und lädt es mit Upload-Keystore, `PLAY_SERVICE_ACCOUNT_JSON` und Repo-Variable `PLAY_UPLOAD=true` in den internen Play-Test. Die Variable erst nach dem ersten manuellen Upload setzen. Android lädt auch bei Release-Tags und manuellen Starts hoch, dann vom ausgewählten Branch oder Tag. iOS geht nur bei einem Tag `v*` oder mit `gh workflow run mobile.yml` zu TestFlight (macOS-Minuten zählen zehnfach). Manuelle Läufe verteilen nur intern, gepushte Release-Tags zusätzlich extern mit Beta-Prüfung. Tags setzen Agenten nur nach Robins Ja. Bei App-Änderungen, die Nutzer merken, fragen sie im Abschluss danach (Skill `push-deploy`). Der Job `testflight` prüft die interne Sichtbarkeit und verteilt Release-Builds; Einrichtung und Wiederholung stehen im README unter „Release“.
- Prüfen: Bei einem deployrelevanten Push `gh run watch`. Der Deploy-Job ist erst grün, wenn `https://<slug>.pleasance.org/api/health` den Commit als `revision` meldet. Wird der CI-Lauf durch `paths-ignore` übersprungen, gibt es für diesen Commit keinen CI-Lauf und die Live-Revision bleibt unverändert.
- Nur hier in der Vorlage: `.github/workflows/standards.yml` baut `standards/` als Image `starter-site` und deployt es über das Tailnet nach https://standards.pleasance.org (Coolify VPS 3, nur aus dem Tailnet). Aus der Vorlage erzeugte Repos überspringen den Workflow und können ihn mit `standards/` löschen.

## Fallen

- Play App Signing: Google verwendet für ausgelieferte Apps einen eigenen App-Signaturschlüssel. Dessen SHA-1 zusätzlich beim Android-Maps-Key erlauben (falls genutzt), dessen SHA-256 neben dem Upload-Key in `ANDROID_CERT_SHA256` für `/.well-known/assetlinks.json` aufnehmen (App-Links/Passkeys). Fingerprints stehen in der Play Console, README „Release“.
- Secret-Scan: Gitleaks 8.30.1 liest zusätzlich zu `--gitleaks-ignore-path` auch `.gitleaksignore` aus dem Checkout. Der Workflow ersetzt diese Datei deshalb ebenfalls durch die Fassung aus `CONFIG_REF`, bei Fork-PRs also aus dem Base-Commit.
- Was hier geändert wird, landet in jedem neuen Projekt und über das Nacht-Review als Befund in allen bestehenden. Konventionen nur ändern, wenn sie für alle Prototypen gelten.
- `standards/` liest die Tabellen „Farbband“ und „Produktfarbe“ aus DESIGN.md: Spaltenreihenfolge und Ausschnitte im Format `1,00–1,35` beibehalten. Zeichnungen der Zeichen stehen in `SIGNS` in `standards/main.js`, ein neues Produkt bekommt dort bis dahin einen Punkt.

## Konventionen

Stack und Aufbau: siehe README.md. Gestaltung: siehe DESIGN.md.

- Neue Tabelle: `packages/db/src/schema.ts` ändern, `bun run db:generate`. Die Migration läuft beim nächsten API-Start, `migrateDb` lässt mehrere Instanzen nacheinander migrieren. Jede Migration muss mit dem noch laufenden alten Code funktionieren: Spalten nullable oder mit Default hinzufügen, Umbenennen und Löschen erst im Deploy danach. Nichts von Hand in der Datenbank ändern.
- Korrelierte Subselects in `sql`-Templates: Bei einem `select` aus nur einer Tabelle rendert Drizzle Spalten ohne Tabellennamen, auch im Template. `exists (select 1 from ${subs} where ${subs.userId} = ${users.id})` wird zu `where "user_id" = "id"`, `"id"` meint dann die Spalte des Subselects, das Ergebnis ist ohne Fehler falsch. Solche Subselects nur in Abfragen mit Join oder mit `alias()`, sonst zwei einfache Abfragen.
- Neue Route: Datei in `apps/api/src/routes`, in `app.ts` einhängen. `requireAuth` für eingeloggte Nutzer, `requireAdmin` für Admins aus `ADMIN_EMAILS` (jeweils allein, danach `c.get('user')`), `validJson(schema)` mit dem Schema aus `packages/shared`.
- Jeder sichtbare Text steht auf Deutsch und Englisch: für Web, API und CLI in `packages/shared/src/messages.ts`, für die App in `lib/core/messages.dart`. Fehlt eine Sprache, schlagen `bun run check` bzw. `flutter analyze` fehl. Im Web `t()` aus `$lib/i18n`, in der API `t(c)` aus `lib/i18n.ts`, in der App `ref.watch(messagesProvider)`. Eigene zod-Meldungen sind Schlüssel aus `messages.ts`. Umgeschaltet wird im `PleasanceFooter`.
- CLI (README, „CLI“): Jedes Kern-Feature bekommt im selben Zug einen Befehl in `apps/cli/src/commands` nach dem Beispiel `settings.ts`, mit Text und `--json` und einem Test in `cli.test.ts`. Die CLI spricht nur mit der HTTP-API, nie mit der Datenbank, so gelten Rechte, Rate-Limits und die Registrierungssperre. Agenten melden sie nur mit admin@pleasance.org an (`login-link <slug> | <slug> login --link -`), nie mit Kundenkonten.
- Fehler antworten immer als `{ error: string }` mit einem Text aus `t(c)`, also in der Sprache, die der Client per `Accept-Language` schickt. Das Web zeigt ihn als Toast.
- Alles, was Mails verschickt oder Geheimnisse prüft, bekommt ein `rateLimit` aus `lib/rate-limit.ts`. Die Zähler liegen in Postgres und gelten für alle API-Instanzen.
- Öffentliche Formulare ohne Login, die Mails verschicken oder Daten anlegen, prüfen ALTCHA (README, „ALTCHA“): `requireAltcha` vor `validJson`, im Web `Altcha.svelte` im Formular, in der App wie `requestCode`. Nicht für Links aus Mails wie Abmelden oder Login-Link, die tragen schon ein Geheimnis.
- Mails über `sendMail` aus `lib/mail.ts`, im Design der Vorlage dort (DESIGN.md, „Mails“).
- Update-Mails (README, „Update-Mails“): nur mit Opt-in, Standard aus. Agenten schreiben Entwürfe als `updates/<datum>-<thema>.md` in beiden Sprachen, senden darf nur ein Admin aus `ADMIN_EMAILS` in `/admin/updates`. Kein Agent löst den Versand aus, auch nicht per API oder Datenbank. Jede Massenmail an Nutzer läuft über diesen Weg, also mit Abmeldelink und `List-Unsubscribe`.
- Registrierung geschlossen bis zu Robins Go: Neue Konten nur für Adressen in `SIGNUP_ALLOWLIST`, bestehende melden sich immer an. `SIGNUP_OPEN=true` erst nach Robins ausdrücklichem Go setzen (README, „Registrierung öffnen“). Tester lädt ein Admin aus `ADMIN_EMAILS` in der App ein (`/auth/invite`, Seite `/invite`), das öffnet nichts. Dort steht robin@pleasance.org, der menschliche Admin. admin@pleasance.org, der agentische Admin für die Savor-Vorschau, kommt nie in `ADMIN_EMAILS`, sonst legen Agenten Konten an und mailen Dritte. Wer einen weiteren Weg baut, auf dem Konten entstehen (z. B. Nostr-Login), prüft dort ebenfalls `mayLogIn` aus `lib/signup.ts`. Öffentliche Seiten ohne Login bleiben davon unberührt.
- Login: Die Mail des Webs trägt Link und Code, die App bekommt nur den Code. Sessions laufen 365 Tage und verlängern sich bei Nutzung. Passkeys (README, „Passkeys“) entstehen nur hinter einer Session, also nur für bestehende Konten. Sie hängen an der Domain aus `APP_URL`: Zieht ein Prototyp zu 1.0 auf eine eigene Domain, gelten die alten nicht mehr und Nutzer melden sich einmal per Mail an. Für Passkeys in der App braucht die API `APPLE_TEAM_ID` und `ANDROID_CERT_SHA256`, iOS die Domain in `ios/Runner/Runner.entitlements`.
- Zustandslos, damit eine App ohne Umbau auf einen anderen Server umzieht oder repliziert hinter einem Load Balancer läuft (`infra.md`, „Skalierung“): Platte und Prozessspeicher halten keinen Zustand, der eine Instanz überlebt oder für alle gelten muss. Sessions, Rate-Limits und Feedback liegen schon in Postgres. Uploads und Medien gehen nach S3 (Hetzner Object Storage, Bucket nach Namensregel) über `Bun.s3`, das `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_ENDPOINT` und `S3_BUCKET` selbst aus der Env liest. Ein neuer Bucket kommt im selben Zug ins nächtliche Backup: Eintrag in `APP_BUCKETS` und Bucket-Policy für `vps1-restic` (`infra.md`, VPS 1, restic, „App-Buckets“). Kein Volume außer `pgdata`. Locks per `pg_advisory_xact_lock`. Caches im Speicher nur, wenn jede Instanz sie verlieren darf, ein geteilter Cache läuft als Valkey-Container in `docker-compose.prod.yml`.
- Hintergrundjobs und Zeitpläne laufen nie im API-Prozess, sondern als eigene Rolle: Service `worker` in `docker-compose.prod.yml` aus dem API-Image mit eigenem Einstieg `apps/api/src/worker.ts`, dort laufen schon die Update-Mails. Neue Jobs kommen als weitere Schleife oder Aufgabe dazu. Aufträge sind Zeilen in Postgres, der Worker holt sie mit `FOR UPDATE SKIP LOCKED`. Fällige Zeitpläne beansprucht er atomar (`update … set next_run = … where name = … and next_run <= now() returning`). So führt auch bei mehreren Workern nur einer jeden Auftrag aus, und kein Job geht bei einem Neustart verloren. Nichts in `setTimeout`, `setInterval` oder Listen im Speicher. Kurze Nacharbeit einer Anfrage wie eine Mail bleibt in der Anfrage.
- Jede Rolle hat einen Healthcheck im Image: API `/api/health` (mit Datenbank), Web `/health` (nur der Prozess), ein Worker ein `/health` auf einem eigenen Port. Uptime Kuma und ein Load Balancer prüfen `/api/health` über die öffentliche Adresse.
- Jede Rolle behandelt `SIGTERM` und `SIGINT`: keine neue Arbeit annehmen, laufende Anfragen bzw. Jobs samt Transaktion abwarten, dann den Datenbank-Pool schließen. Wartepausen müssen sofort abbrechbar sein. Compose begrenzt den Shutdown auf 30 Sekunden; neue Jobs und Anfragen müssen in dieses Budget passen. Der API-Test prüft den Shutdown in echten Unterprozessen.
- Replikation und Proxy-Kette: README, „Stoppen und weitere Instanzen“. Weitere Instanzen verwenden dieselbe private Datenbank per Compose-Override, der Standard bleibt bei lokalem Postgres. `clientIp` liest den letzten `X-Forwarded-For`-Eintrag: Traefik hinter einem LB hängt dort standardmäßig die LB-IP an, auch mit `forwardedHeaders.trustedIPs`. Vor dem Betrieb echte und gefälschte Client-Header durch die gesamte Kette testen, sonst teilen sich alle Nutzer die IP-Limits. Nie ungeprüft den ersten Eintrag verwenden.
- Konfiguration nur über die Env: Jede neue Variable steht in `.env.example`, `.env.production.example` und `docker-compose.prod.yml`. Im Code keine Domains, IPs, Hostnamen oder Pfade des Servers. Service-Namen aus der Compose-Datei (`api`, `postgres`) sind erlaubt.
- Postgres hat im Compose eine Speichergrenze (`POSTGRES_MEMORY`, Standard `512m`). Wird sie eng, in Coolify erhöhen, nicht entfernen.
- Der Feedback-Knopf bleibt in jedem Prototyp, auch ab 1.0: Dann ist der Käfer nur im Testmodus sichtbar, „Feedback geben“ immer (README, „Feedback“). Eigene Overlays, die nicht auf den Screenshot sollen, bekommen im Web `data-feedback-ignore`. Neue API-Aufrufe laufen über `api` bzw. `apiProvider`, sonst fehlen ihre Fehler in den Meldungen. Offene Meldungen eines Repos: `gh issue list --label feedback`.
- `users.name` ist ein freier Anzeigename ohne Filter. Bekommt ein Prototyp eindeutige öffentliche Handles (z. B. `/@name`): NFKC-normalisiert und kleingeschrieben speichern und eindeutig machen, reservierte Namen sperren (`admin`, `root`, `api`, `support`, `www`, `login`, `settings`, dazu alle eigenen Routen). Einen Wortfilter für Vulgäres gibt es nur bei öffentlichen Community-Apps, dann mit `obscenity`. Eigene Wortlisten erzeugen Fehltreffer.
- Web: API-Aufrufe über `api` aus `$lib/api`, Login-Zustand aus `$lib/auth.svelte`. Seiten hinter dem Login unter `routes/(app)`.
- Externe Quellen im Browser (Skripte, Fonts, Bilder, APIs) in die CSP in `apps/web/svelte.config.js` eintragen, sonst blockt der Browser sie. Der Browser-Test in `apps/web/tests` läuft gegen den Produktions-Build und scheitert an jedem Konsolenfehler, also auch an CSP-Verstößen. Inline-`<style>` erlaubt die CSP nur im Dev-Modus: Setzt eine Bibliothek eigene Styles (etwa Web Components im Shadow-DOM), kommen deren Hashes in `style-src`.
- Eine Abhängigkeit patchen: `bun patch <paket>`, die Datei landet in `patches/` und in `patchedDependencies`. Beide Dockerfiles brauchen dann `COPY patches patches` vor `bun install --frozen-lockfile`, sonst scheitert der Build.
- Mobile (`apps/mobile`): API-Aufrufe über `apiProvider`, Login-Zustand aus `authProvider`, Seiten in `lib/features/<name>`, Routen in `lib/core/router.dart`. DTOs von Hand schreiben wie `User` in `core/auth.dart`. OpenAPI aus zod mit generiertem Client erst, wenn die API stabil ist.
- Update-Pflicht (README, „Update-Pflicht“): Vor dem ersten Store-Build `appStoreId` in `lib/config.dart` setzen, sonst bleiben alte Versionen unerreichbar. Die App sendet `X-App-Platform` und `X-App-Build` (CI-Run-Nummer), unter `MIN_BUILD_IOS`/`MIN_BUILD_ANDROID` antwortet die API außer auf Feedback mit 426 und die App zeigt nur den Update-Screen. Ein Minimum erst anheben, wenn ein neuerer Build in diesem Store live ist. Web und lokale Builds senden nichts und werden nie gesperrt. Eine Share-Extension oder ein anderer nativer Client sendet dieselben Header.
- Mobile-Karte: flutter_map mit OSM. Google Maps nur, wenn Google-Places-Daten nötig sind (wie doener).
- Mobile bei Bedarf: sembast für Offline und Sync (Vorbild doener). Kein eigener Dart-Server, kein Supabase.
- Repos sind öffentlich, auch ihre CI-Logs. GitHubs Push Protection blockt bekannte Token-Formate schon beim Push, `secrets.yml` scannt danach jeden Push und PR mit gitleaks (README, „Secret-Scan“). Fehlalarme eng abfangen, per Fingerprint in `.gitleaksignore` oder per Pfad und Regel in `.gitleaks.toml`, nie eine Regel ganz abschalten. Ein echter Fund ist schon öffentlich: das Secret sofort rotieren.
- Keine Secrets im Client: Alles in Web-Bundle und App lässt sich auslesen, mit LLMs auch aus kompilierten Apps. Berechtigungen und Zahlungen prüft nur der Server. Release-Builds der App laufen mit `--obfuscate --split-debug-info`, das macht sie kleiner und nimmt Klassen- und Funktionsnamen heraus, ist aber kein Schutz. Weitere Verschleierung (String-Verschlüsselung, kommerzielle Tools) nicht. Stacktraces symbolisieren: README, „Release“.
- LLM-Aufrufe (erst, wenn ein Prototyp sie braucht): Prompt Injection lässt sich nicht per Prompt verhindern, nur durch Grenzen. Ein Modell, das Nutzer- oder Fremdtext liest, bekommt keine Tools und keine Zugangsdaten außer dem eigenen API-Key. Fremdtext steht escaped und abgegrenzt im Prompt (z. B. `<report>…</report>`, Hinweis im System-Prompt), die Antwort kommt als strukturierte Ausgabe mit zod-Schema. Geld, Rechte, Mails an Dritte und Löschungen hängen nie allein an einer Modellantwort: dazu eine deterministische Obergrenze (z. B. pro Nutzer und Zeitraum) oder die Bestätigung eines Menschen. Angezeigte Modellausgaben gelten als Nutzereingabe: escapen, Links und Markdown nicht ungeprüft rendern. Vorbild: fieldtest, `apps/api/src/lib/evaluate.ts`.
- Push (FCM, APNs, Web Push) erst, wenn ein Prototyp ihn braucht. Ein Push ist nur ein Signal: Ereignistyp und Objekt-ID oder Cursor, keine Inhalte und keine personenbezogenen Daten, wegen des Datenschutzes (Grundsätze 1 und 2). Die App holt die Daten über einen Endpunkt hinter `requireAuth` ab ihrem letzten Cursor (`since`) und fragt ihn auch beim Öffnen und regelmäßig ab, so schaden verlorene oder doppelte Pushes nicht (Vorbild Gmail: `users.watch` meldet nur eine `historyId`, `history.list` liefert die Änderungen). Live-Events im Web folgen demselben Muster, etwa SSE über Postgres `NOTIFY` mit nur IDs im Payload wie in music-hub (`services/sse.ts`).
- Benachrichtigungen (Push, Mail, Hinweise in der App) baut der erste Prototyp, der sie braucht, nach diesen Mustern aus den REA-Teardowns (`Mirksen/rea`, `reports/*/ux-und-technik.md`): Nur Transaktionales und was der Nutzer abonniert hat, keine Marketing-Pushes, keine Werbe-Hinweise in der App, keine Marketing-SDKs (Braze, MoEngage, Customer.io, Salesforce MC). Massenkommunikation läuft nur über Update-Mails. Die Einstellungen liegen pro Nutzer auf dem Server: jede Kategorie einzeln abbestellbar, Ruhezeiten (Wochentag, Beginn, Ende) und Pausieren. Das Gerät meldet bei der Registrierung Zeitzone und Sprache, zugestellt wird zur lokalen Uhrzeit. Mehrere Ereignisse werden gekappt und zusammengefasst statt einzeln gemeldet, jede Meldung bietet „Weniger davon“ direkt an. Aufs Handy erst, wenn die Meldung im Web ungesehen blieb. Gelesen ist ein Serverzustand pro Benachrichtigung und gilt auf allen Geräten. Kappung, Ruhezeiten und Staffelung entscheidet der Worker beim Zustellen. Vorbilder: Gmail (Kappung, gelesen überall), GitHub (Ruhezeiten), Reddit (Zeitzone), Notion (Staffelung), Google Business Profile („Weniger davon“).
- Screenshots für pleasance.org: Kernscreens als öffentliche Seiten in `PAGES` in `apps/web/screenshots.ts` eintragen, die CI fotografiert sie nach jedem Deploy (README, „Screenshots“). Seiten hinter dem Login nicht, die CI hat keinen Login und die Bilder zeigen keine echten Nutzerdaten. Der Bot committet die Bilder auf `main`, vor dem Push also holen.
- Link-Vorschau: Das Layout setzt die `og:`-Tags, das Bild rendert `bun run og-image` in `apps/web` (DESIGN.md, „Vorschaubild“). Danach neu rendern und committen, wenn sich `APP_NAME`, `APP_BAND`, `tagline` oder die Kachel ändern. Die Kachel liegt als `static/favicon.svg`, dieselbe wie `img/werkzeuge/<slug>.svg` im pleasance-Repo. Öffentliche Seiten mit eigenem Inhalt, etwa geteilte Links, geben im Server-Load `meta` mit Titel, Beschreibung und optional einem absoluten Bild-URL zurück. Private Inhalte, Links mit Passwort, abgelaufene und ungültige Links bekommen die allgemeine Vorschau. Link-Crawler führen kein JavaScript aus, also wirkt `meta` nur in `+page.server.ts` bzw. `+page.ts` auf Seiten mit SSR, nicht unter `routes/(app)` (`ssr = false`). WhatsApp speichert Vorschauen lange zwischen.
- Für Agenten lesbar (README, „Für Agenten“): Jede öffentliche Seite mit eigenem Inhalt steht in `publicPages` in `apps/api/src/lib/public-pages.ts`, mit Titel, Beschreibung und ihrem Inhalt als Markdown in `body`, in der Sprache aus `m`. Daraus entstehen `/llms.txt`, `/llms-full.txt` und `<seite>.md`. Eine neue öffentliche Seite kommt im selben Zug dazu, der Browser-Test prüft, dass jede eingetragene Seite existiert und jede `<h2>` der Seite als `## `-Zeile im Markdown steht. Hinein kommt nur, was jeder ohne Login sieht: nichts unter `routes/(app)`, keine Konten, keine Admin-Seiten, keine Links mit Passwort, keine abgelaufenen. Inhalte einzelner Nutzer nur, wenn sie sie für alle veröffentlicht haben. `publicPages` lädt bei jedem Aufruf alle Seiten: Bei Tausenden Einträgen die Abfrage auf das Wichtigste begrenzen oder eine Übersichtsseite pro Sammlung eintragen. Eine öffentliche JSON-API mit OpenAPI oder einen MCP-Server baut erst der Prototyp, dessen öffentliche Daten sich durchsuchen lassen sollen, aus `publicPages` mit `hono-openapi` bzw. dem offiziellen MCP-SDK, und zieht es hier nach.
- Formatierung und Lint: Biome, Regeln in `biome.json`. `bun run format` behebt das meiste selbst.
- Strenges TypeScript, denn der Compiler ist die schnellste Rückmeldung: Die tsconfigs setzen `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride` und `noFallthroughCasesInSwitch`, Biome verbietet `any` (`noExplicitAny`, `noImplicitAnyLet`, `noEvolvingTypes`). Unbekanntes ist `unknown` und wird mit zod gelesen: Bodies per `validJson`, die Env per Schema in `apps/api/src/env.ts` (die Einstiege importieren es zuerst, eine neue Variable mit Pflichtwert oder Format kommt dazu), Antworten fremder APIs und `localStorage` per `safeParse`. Optionale Felder in Schemas, die an Bibliothekstypen gehen, mit `.exactOptional()`. Ein `switch` über eine Union endet mit `default: { const unhandled: never = value; throw new Error(String(unhandled)); }`. Typfehler an der Ursache beheben, nicht mit `as`, `@ts-expect-error` oder `biome-ignore` überdecken; `!` nur, wo der Wert sicher da ist (etwa nach `insert … returning`).
- Apple-Zugangsdaten der Prototype Factory stehen zentral in `~/.secrets`: `APPLE_TEAM_ID`, `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8` (base64), dazu das CI-Signing-Zertifikat `APPLE_CI_DEV_CERTIFICATE_BASE64` (base64-PKCS12) und `APPLE_CI_DEV_CERTIFICATE_PASSWORD`. Ablage und Kopien: `~/dev/kontor/infra.md`, Abschnitt „Zugangsdaten: wo liegt was“. Im selben Aufruf mit `set -a; . ~/.secrets; set +a` laden; Werte nie ausgeben oder ins Repo schreiben. Nach Freigabe richtet `~/dev/kontor/apple-ci-secrets.sh robinchoice/<repo>` die GitHub-CI ein: ASC-IDs als Variablen, `ASC_KEY_P8`, `IOS_DEV_CERTIFICATE` und `IOS_DEV_CERTIFICATE_PASSWORD` als Secrets.
